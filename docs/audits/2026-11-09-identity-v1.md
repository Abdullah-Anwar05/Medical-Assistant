# Code audit — Identity v1 (2026-11-09)

Scope: all code at commit `1b23137`. Audited against CLAUDE.md coding standards (SOLID, Clean Architecture,
best practices, no duplication) and CODE_REVIEW.md. Result: **FAIL**. Behaviour is correct and well tested;
structure does not meet the new standards.

## API (`api/`) — owner: API thread

| # | Severity | Finding | Required fix |
|---|---|---|---|
| A1 | High | Clean Architecture: Identity is one project (`Identity.Api`) with Domain/Data/Endpoints/Security as folders. | Split into `Identity.Domain`, `Identity.Application`, `Identity.Infrastructure`, `Identity.Api`; references point inward only. Domain has no EF Core/ASP.NET references. |
| A2 | High | SRP: `Endpoints/IdentityEndpoints.cs` (372 lines) holds validation, lockout policy, token rotation, reuse detection, persistence, audit and cookie handling. | Endpoints only map HTTP to use cases. Move each flow to an Application use case (`RegisterUser`, `LoginUser`, `RefreshSession`, `Logout`, `GetCurrentUser`) returning a result type; the Api layer maps results to HTTP. |
| A3 | High | DIP: handlers depend directly on `IdentityDbContext` and the concrete `TokenService`. | Application defines ports (`IUserRepository`, `IRefreshTokenStore`, `ILoginAttemptStore`, `ITokenIssuer`, `IUnitOfWork`); Infrastructure implements them. |
| A4 | Medium | Domain is anaemic: lockout rules (`FailedCount`, `LockedUntil`, reset on expiry) and token rotation/revocation live in the endpoint. | Move them into domain behaviour (`LoginAttempt.RecordFailure(now)`, `RefreshToken.Rotate(...)`, `Revoke(reason)`), unit-tested without a database. |
| A5 | Medium | Duplication: "revoke all active tokens in family with reason" is written three times (reuse, logout, rotation path); the 409 problem is built twice. | One store method `RevokeFamily(familyId, reason, now)`; one error factory. |
| A6 | Medium | Validation is hand-rolled inside the handler. | Request validators in Application (one per request), reused by the endpoints; no inline rules. |
| A7 | Low | Mutable static `_dummyHash` (thread-unsafe lazy init) in a static class. | Inject a singleton timing-equaliser service. |
| A8 | Low | Delivery concerns (`X-Client` detection, cookie read/write) are mixed into handlers. | One Api-layer `ITokenDelivery` (web cookie vs mobile body) used by every endpoint. |

## Web + Mobile — owners: Web thread, Mobile thread

| # | Severity | Finding | Required fix |
|---|---|---|---|
| C1 | High | Duplication across clients: `api/types.ts` (contract types, roles), the ApiError / Problem Details parsing, register validation (`MIN_PASSWORD = 12` and rules) and the refresh/session logic are written twice, already drifting (web has `ROLES`/`STAFF_ROLES`, mobile does not). | One shared TypeScript package (proposed `packages/client-core`) consumed by both: contract types, roles, API client core with pluggable token delivery, ApiError, validators. **Needs an ownership decision.** |
| C2 | Medium | Clean Architecture in clients: validation and submit logic live inside page/screen components (`RegisterPage.tsx`, `RegisterScreen.tsx`). | Components render only; form logic moves to hooks (`useRegisterForm`) that call shared validators and services. |
| C3 | Low | Silent `catch {}` blocks in both API clients (`web/src/api/client.ts:42`, `mobile/src/api/client.ts:59,153,161`). | Each one either handles a named expected case with a comment-free explicit branch or surfaces the error; no blanket swallow. |
| C4 | Low | Each client has a design-token file (`styles.css`, `theme.ts`) with the same palette values. | Palette values exported once from the shared package. |

## Not flagged

Security posture is good: no secrets in the repo, HttpOnly/Secure/SameSite cookie, hashed refresh tokens,
rotation with reuse detection, timing-equalised unknown-user login, no user enumeration on login/423.
Tests: 32 API (SQLite + PostgreSQL), 13 web, 20 mobile.

## Re-audit (2026-11-09) — PASS

- A1–A8 fixed: `Identity.Domain` (no references) ← `Identity.Application` ← `Identity.Infrastructure` ← `Identity.Api`; endpoints are 72 lines of HTTP mapping; ports and use cases live in Application; lockout and rotation rules live on domain entities with 26 unit tests; revoke-family logic is in one store method; `TokenDelivery` handles cookie vs body.
- C1–C4 fixed: `packages/client-core` holds the contract types, roles, ApiError, validators, the session manager with pluggable token delivery and the palette. Web and mobile copies are deleted. Remaining `catch` blocks rethrow or map named cases.
- Noted: the refactor added migration `RefreshTokenRevokedAtConcurrency` (a concurrency token on `RevokedAt`); this is a schema change, but the API contract is unchanged.
- Residual (low, follow-up): web `useAuthForm` and mobile `useAuthSubmit` both implement the validate → busy → map-error cycle; this could move into a framework-agnostic helper in client-core.
- Tests: API 26 unit + 32 integration on SQLite and on PostgreSQL, build has 0 warnings; client-core 37; web 16 + lint/build; mobile 14 + typecheck/lint (client tests moved into client-core).
